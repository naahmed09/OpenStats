# openstats-desktop

Front ends for the OpenStats workspace. All application logic is Rust (`openstats-ui`,
exposed through `crates/openstats-host`); what lives here is the thin layer that connects
it to a browser canvas or a native window.

```
web/                 browser front end (no build step, no npm dependencies)
  openstats.js         canvas painter, event wiring, IME, wasm ABI wrapper
  tauri-shell.js     native dialogs / files / clipboard / menu bar / tear-off (Tauri)
  index.html         main workspace page
  graph.html         torn-off graph window
  test/              node:test suites + fixtures generated by the Rust encoder
tauri/src-tauri/     Tauri v2 shell (own Cargo workspace, not part of the repo's)
```

## How the pieces fit

* `openstats-host` compiles to `wasm32-unknown-unknown` as a `cdylib` with a small C ABI
  and no `unsafe` beyond the `#[no_mangle]` exports. Input (keys, pointer, wheel,
  paste, IME, file bytes) goes in through a host-owned buffer; draw commands
  (`OTC1` binary canvas stream) and outcomes (save a file, copy text, print, tear off a
  graph, ask for a file) come back out.
* `openstats.js` maps DOM events to that ABI and paints the command stream onto a
  `<canvas>` 2D context. A hidden `<textarea>` provides keyboard focus, paste and
  input-method composition; the candidate window follows the grid editor's caret.
* The same page runs unchanged inside Tauri. When `window.__TAURI__` exists,
  `tauri-shell.js` swaps in native dialogs, file I/O and clipboard, publishes the
  workspace's menu tree to Rust (`set_menu`) so a native menu bar is built from it, and
  opens graph tear-offs as real windows (`open_graph_window`).

## Deviation from the original plan

The brief named `wasm-bindgen`, `web-sys` and `js-sys`. These are third-party crates,
which the project forbids, so the wasm module uses a plain C ABI and the glue is
hand-written JavaScript. Behaviour is the same; the JS file is the only "binding".

## Build

The scripts in `../scripts` do the work; run them from the repository root.

```sh
scripts/build-web.sh          # wasm module + pages -> dist/web, dist/openstats-web-VERSION.tar.gz
scripts/release.sh            # checks + web bundle + the installer for this OS
scripts/package-macos.sh      # universal .dmg (macOS, Xcode tools, `cargo install tauri-cli --version '^2'`)
pwsh scripts/package-windows.ps1   # .msi + setup .exe (Windows, MSVC build tools, Git for Windows)
```

`build-web.sh` compiles `openstats-host` for `wasm32-unknown-unknown` with the size-optimised `web` profile (`rustup target add wasm32-unknown-unknown` first), runs `wasm-opt -Oz` if it is installed, and checks that every file the pages refer to is in the bundle. Serve `dist/web` from any static host (it includes a `_headers` file for Netlify and Cloudflare Pages: `application/wasm` MIME type, immutable caching, a strict CSP). The Tauri shell embeds the same `dist/web`.

For development: `scripts/build-web.sh`, then `python3 -m http.server -d dist/web 8080` for the browser, or `cd openstats-desktop/tauri/src-tauri && cargo tauri dev` for the desktop app.

Icons are generated by `cargo run -p openstats-host --example make_icons -- openstats-desktop/tauri/src-tauri/icons` (std only; the PNG, ICO and ICNS files are committed).

Signing is optional. macOS: `APPLE_SIGNING_IDENTITY` (and `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID` for notarisation). Windows: `OPENSTATS_WIN_CERT_THUMBPRINT`, optionally `OPENSTATS_WIN_TIMESTAMP_URL`. Unsigned builds work but trigger Gatekeeper / SmartScreen warnings.

## Testing

```sh
cargo test -p openstats-host                       # ABI, end-to-end workflows, release config, script tests
cargo run -p openstats-host --example dump_frame -- openstats-desktop/web/test/fixtures
node --test openstats-desktop/web/test/*.test.mjs  # decoder, painter, events, IME, Tauri glue
```

The fixtures are real Rust output, so the decoder test fails if the encoder and the JS
decoder ever disagree.

## What was and was not verified

Verified in the development environment: the Rust host ABI (native tests), the JS
decoder against real encoder output, the painter, event wiring, IME and the Tauri glue
(all under Node with mock DOM/Tauri objects).

**Not verified:** building the installers (`.dmg`, `.msi`, `.exe`) on their platforms, the GitHub workflows, compiling `openstats-host` for `wasm32-unknown-unknown` (the target was
not installable there), running in a real browser, and compiling or running the Tauri
project (no registry access). Expect to fix small API drift when you first build them.
